# 微信读书抓取：转换与排版规则细节

SKILL.md 只留执行约束与必知规则；本文是各类内容落到 Word／EPUB 的具体做法与判据，改转换代码、排查成品排版时再读。

## 正文是怎么取的

阅读器把正文画在 canvas 上，读 DOM 拿不到字；而正文接口返回的是**整份 base64
被切开的碎片**，切点不对齐还要客户端签名，自己拼块会拼出零星坏字（实测把
「魏晋时代」拼成过「魏晋时c」，只坏几个字节，肉眼很难发现）。

所以走的是：在 cloakbrowser 里打开阅读页，挂钩 `window.atob`——阅读器自己会把
所有碎片拼好后整体解码一次，把那一次的产物抄走，就是干净的原书 XHTML。

细节（地址算法、响应格式、注释的几种写法、登录态续期）见 `protocol.md`。

## 备用：EPUB 打包（默认不生成）

`weread epub <书>` 可以把同一批材料压回一个 EPUB。日常不需要——留着是因为它能
**验证抓取是否完整**（结构自查会把清单、spine、锚点、XML 良构、CSS 引用全查一遍），
排查「是不是漏内容了」时比读 docx 直观。服务端没有整本下载的口子（探测记录见
protocol.md），只能逐章取，但取回来的就是 EPUB 包里那几个文件的原文：

| EPUB 里的东西 | 从哪来 |
| --- | --- |
| `Text/*.xhtml` | 逐章挂钩 `atob` 拿到的原文，一章由多个原文件拼成的会合并成一个 body |
| `Styles/*.css` | 随正文一起下发的原书样式表，内容相同的只存一份 |
| `Images/*` | 绝对地址直接下；相对路径按 `res.weread.qq.com/wrepub/web/<bookId>/<文件名>` 拼 |
| `content.opf` / `nav.xhtml` / `toc.ncx` | 用 `chapterInfos` 的标题与 `level` 现搭，目录带层级 |

打包时只做两处必要的修补，都是为了让书在通用阅读器里真能读：

- **注文还原。** QQ阅读体系把夹注做成一张小图标、注文塞进 `alt`，除了微信读书没人
  认得（那张 `note.png` 对普通出版书还取不到）。统一转成 EPUB3 的
  `epub:type="noteref"` + `<aside epub:type="footnote">`，阅读器就能弹注。
  原本就是锚点式的注只补 `epub:type`，不动结构。
- **断锚点修补。** 有些原书的注文块只写了回跳 `href` 没写 `id`，注号点过去落空
  （《波斯笔记·波斯王陵》整章 21 条都这样）。按已算出的配对关系把 `id` 补回去。

生成后会自动跑结构自查（mimetype 位置与压缩方式、清单与 spine 自洽、id 不重复、
每个 xhtml 是合法 XML、内部引用与锚点都能落地）。

**字体：能取到的会嵌进包里。** `@font-face` 引用的字体和相对图片同一个基址
（`wrepub/web/<bookId>/<文件名>`），取回来存进 `Fonts/` 并改写 `src`；取不到的把整块
`@font-face` 删掉，让阅读器回退系统字体，不留坏引用。《东汉时代的政治与社会》
9 个字体取到 4 个，引文的仿宋体已能正常显示。

**但 PUA 生僻字仍然无解。** 服务端只放常用子集：那本书取不到的几个恰好叫
`ext02` / `ext15`，而第 15 面就是私用区；能取到的 4 个字体里 PUA 字形数为 0。
更麻烦的是有些书（如《治史三书》）连 `@font-face` 都没有，PUA 码位孤零零挂在
正文里，没有任何字形来源——那 2 处 U+E862 是「䴙鹈泉」的**䴙**，微信读书自己也
显示不出来。这类字符生成时会连同上下文列出来，只能人工核定。

## 复杂内容怎么落到 Word

- **注释** → Word 真脚注（`word/footnotes.xml`），页脚自动编号，不是把注文堆在章末。
  认四种写法：注号带 id 的、只有 `href` 的、注号与注文两个 `<a>` **互指对方 id** 的
  （孙英刚《神文时代》那种，class 毫无线索，靠互指本身确证、段首的那个是注文），
  以及微信读书自己插的 `img.qqreader-footnote`（注文藏在 `alt` 里）。配不上的按数量
  顺序兜底；实在配不上的注文降为小字留在原位，不丢内容。
  注号与注文**不在同一个原文件**的也认。同一章的几个文件之间，锚点带着文件名
  （《波斯笔记》第四章、第十三章），渲染前去掉本章自己的文件名，再走章内配对；
  分在两章的（《亲密关系（第8版）》注号在各节、注文集中在「本章小结」），构建前先全书
  扫一遍，注号与注文锚点互指、两边文件归属（章节表 `files`）对得上才配，id 有歧义就不配。
  注文挪进脚注后，只隔着这些注文的分隔线一并不出。注中之注（注文里又夹
  `qqreader-footnote`）Word 没法嵌套，按括注接在原处：「美国人口普查局（U.S. Census Bureau）」。
  `img` 的 `alt` 若包含 XHTML，先解析段落、强调与图片，不把标签印成文字。
  **注文里的图也保得住**：`footnotes.xml` 有自己的关系分部（图片本体与正文共用，
  只复制关系项），所以注里夹的生僻字图不会变成占位符。
- **图片** → 按类名里的 `alone50/80/100` 定宽（那就是原书相对版心的百分比），
  居中单独成段，超高的自动缩到一页内。图说紧跟其后用楷体小字，保留其中的换行与
  署名。生僻字图（`inline-character`）按行内嵌、与正文等高。下载失败会在原位留
  「〔图片下载失败〕」而不是静默丢掉。
- **表格** → 还原 colspan/rowspan 合并，加细边框，表头加粗并跨页重复。
  注意：微信读书的书里**大多数表格在制书阶段就被拍成了图片**，真 `<table>` 少见。
- **样式** → 字号、字体族（宋/楷/仿宋/黑）、颜色、对齐、首行缩进、左缩进，全部从
  **每章自带的原书 CSS** 求值，不认死出版社的类名，所以换书不会失效。出版社的设计
  会照搬：比如《治史三书》的标题是绿色 #0F7E2B、引文用楷体，成品里都留着。
  唯一一处主动改写是**正文字体**：Kindle 转制常把整本正文设成某种黑体
  （《治史三书》与《金明館叢稿初編》都是「汉仪旗黑50S」），整本黑体在 Word 里没法读，
  所以正文里的黑体按宋体落地——**只管正文，标题的黑体照留**。判据用占比（≥20%）
  而不是「哪种字体最多」：陈寅恪那类书里成段的楷体引文极多，按众数判会被稀释成
  「主体是楷体」，于是他自己的正文就留在黑体里了。占比按章算、也按全书算，任一达标就转：
  只按章算还会被稀释——章首导语后面跟一长串楷体要点，或者索引全是短条目，那一章就漏转
  （《亲密关系（第8版）》第14章、《何枝可依》自序、《神文时代》书名索引）。一章由几个原文件
  拼成时所有文件一起算，不能只看第一个（第一个常是只有标题的标题页）。
  上下标认 CSS 的 `vertical-align: super/sub`（出版社多用 `span.super`/`span.sub` 而不是
  `<sup>`，不认的话「10⁸」印成「108」），字号退回正文，免得跟 Word 上下标自带的缩小叠加。
- **图说** → 取自图后的 `p.picture-txt` 一类段落。`alt` 只有像人话时才当图说
  （含汉字、长于 6 字、不是 `copyright-1`/`q1` 这种制作标识），否则会把文件名印进正文。
- **大纲** → 章节层级取自接口的 `level`，章内标题按 h 标签深度顺延，Word 侧栏导航
  直接可用。有些书的标题是一张美术字图片（真文字在 `title` 属性和章节表里），
  这种情况用文字做标题、把图挪到下一段，免得导航窗格里出现一串没有文字的条目；
  但标题里若夹着注释图（注文在 `alt` 里）会留在原地转成脚注，不会被当装饰图挪走。
  章标题拆成几行的（「第1章」「人际关系的构成」各是一个 h1）拼回一条。认章标题的次序是
  整条相等 → 相邻两三个拼起来相等 → 最后才用「包含」兜底：只按包含认，会随字数长短把
  半条当整条，结果章名降级、与「第N章」顺序颠倒，或者两截各成一个二级标题。
- **生僻字图** → 更常见的做法是把生僻字直接拍成图嵌在行内（陈寅恪《金明館叢稿初編》
  里的「黄法𣰋」就是这样）。这类图**必须按高度定尺寸**：按 `data-w` 的宽度算的话，
  一个字会变成五厘米宽的大图横在句子中间。方块字图一律按一个字高排，CSS 里写的
  `height: 1.8em` 是给阅读器留白用的，照搬到 Word 会明显大过周围的字。
- **生僻字** → 有些书把生僻字编在私用区（PUA），靠嵌入字体显示，而微信读书只发
  常用字体子集，这些字到手就是个空码位。处理办法是查本机字体 cmap 的等价关系：
  不少中文字体会把私用区码位与该字真正的 Unicode 码位映到同一个字形，命中即是确证
  （实例：Hiragino Sans GB 里 U+4D19「䴙」与 U+E862 同为 cid22124，于是《治史三书》
  的「▮鹈泉」还原成「䴙鹈泉」）。查不到真字的**码位原样保留，只对该字符加黄色高亮**（正文、脚注相同），
  不得连带高亮同一 run 中的正常文字，更不能整段高亮。另一个允许的黄色标记是
  随文图片下载失败时的 `〔?〕`；不把高亮用作自动重点标记。绝不静默丢失。单独查某个字：`lib/pua.py U+E862`。
- **平台声明** → 版权页里「本书由…授权微信读书制作与发行」这类平台自插的发行声明
  会滤掉（只匹配这一类窄模式，出版社原有的版权文字照留），成品统计里会报滤了几处。

## 书前目录（`--toc`）

默认不排——成品靠 Word 侧栏大纲导航（2026-09-04 定）。排的时候条目取**正文里实际排出的标题**，
深度跟章节表走（接口列到几级就排几级）；不直接照 `chapterInfos` 排，因为接口只列它切开的文件，
同一文件里的小节不单列，《失控》每章的「x.1」就这样整整漏了 24 条。不用 Word 目录域、不做跳转，
目录条目不占大纲级别。`--chapters` 分几次抓不同章也没问题：`book.json` 始终存全量章节表，
`build` 会把已抓到的按全书顺序拼起来。

## 繁体底本的书

以繁体为底本的书（如上海古籍《金明館叢稿初編》），微信读书会把**繁简两套正文
一起下发**在同一份 XHTML 里，用 class 区分，阅读器靠 CSS 只显示一套：

```html
<h1 class="wr-traditional text-title-1-c">出版説明</h1>
<h1 class="wr-simplified  text-title-1-c">出版说明</h1>
<p  class="wr-traditional preface-text">陳寅恪先生作爲二十世紀……</p>
```

不挑的话整本书会输出两遍。默认取**繁体**（`--variant simplified` 可改）。
接口返回的书名作者即使在繁体本里也是简体，**照搬原值不转**——那是平台的元数据，
转它就是改数据，而且文件名也用同一份原值，两边一致。只有「目　录」这类我们自己
加的标签会跟着正文用繁体。

生成后会顺带查一遍繁体正文里的简体残留（平台自己转换没转干净，实测《金明館叢稿
初編·出版説明》里就有「标点」）。**只报告不改**：擅自转换等于改动原书；而且 opencc
的 s2t 偏激进，会把繁体通用的异体字（迹/蹟、周/週、搜/蒐、别/別）也算进来，
所以那份清单是「疑似」，要由人甄别。

## 正文字体与缺字

默认正文用**中华书局宋体**。选它不是为了好看，是为了收字：实测本机各字体的汉字
覆盖，宋体、楷体、仿宋、黑体的**扩展B 收字都是 0**，而中华书局宋体扩展B 收 42713 个
（几乎全覆盖）、扩展C-F 收 17606 个。

麻烦在于它**按 Unicode 平面拆成四个独立字族**（00平面＝基本多文种平面、
02平面＝扩展B/C、15平面与16平面＝私用区古籍造字）。只把正文字体名写成
`中华书局宋体00平面` 的话，扩展B 的字照样落到 Word 的默认回退上，等于没换。
所以 `lib/fontcover.py` 为每个字族建了码位覆盖表，落盘时**按字符切 run**：
常用字仍走正文字体，只有它缺的字才切出来单独指定备用字体，整段观感不受影响。
借了多少字会在统计里报。

两条硬规矩：

- **私用区码位绝不借字。** 各家的 PUA 是各自的造字约定，借中华书局的字形来显示
  别家的 PUA 码位，会渲出另一个字，而且错得无声无息。这类字只走 `lib/pua.py`
  的 cmap 等价查证，查不到就留空并高亮。
- 本机没装指定字体时退回宋体并在统计里说明，不静默降级。

顺带一提：微信读书的书其实极少用到扩展区（实测五本书 40 万字里只出现 1 个扩展A
字），所以这主要是给日后可能遇到的古籍类材料上的保险。单独查覆盖：
`lib/fontcover.py 中华书局宋体 "要检查的文字"`。

## 输出约定

- 版式：A4，左右边距 3cm；未被原书样式覆盖的正文默认中华书局宋体 11pt、
  行距 1.5、首行缩进 2 字。**这不是强制所有段落用宋体。** 原书明确设置的仿宋、
  楷体段落保留；导读或附录很长时，仿宋可能超过半本，不能按占比或 `preface-text`
  类名就认定错误。先对照 CSS 和段落内容。只有上文约定的正文黑体转换是默认例外。
  用户明确要求统一字体时才另作调整，不能为了通过验收自动抹掉原书字体层次。
- 文件名为 `<书名>_<作者>.docx`。书目字段里的**营销标签**（`【中华书局出品】`
  `【赠…】`，以及括注形式的 `（曾鸣教授全新商业思考）` 这类宣传语）、**装帧**（`（精）`）、
  **册数**（`全二册`、`（上、下）`、`（上中下）`、`（3册）`——几册已合成一本电子书）与单人署名的**角色词**（`马昕著`→`马昕`）会去掉；**版次**
  （`增订版`/`第8版`）、**丛书名**、**丛书编号**（`【译丛067】`）是书目信息，一律保留。
  括注的判据是「含营销词且不含书目词」（`lib/titles.py`），两边都保守：宁可漏删，
  也不误伤版次。只收一册的 `（上）`、`（第一册）` 是书目信息，删了会和另一册撞成同一个
  文件名，留着；`（1-3册）` 这种区间是不是全套光看题名判断不了，脚本不猜，报「题名待核」。
  清理不干净时会报「题名待核」，此时用 `--out` 自己指定文件名——**营销标签平台
  随时造新词，正则追不全，所以宁可漏检并提醒，不做激进删除**。
- **版权页的「书名：」一行跟着同一套规则清理**（扉页、文件名、版权页三处同题名，
  不能自相矛盾；版权页其余文字一个字不动），统计里会报清了几处。
- 制书方留在正文里的**编辑注释**（`<!-- replace below with real src -->` 一类）不是
  书的内容，阅读器也不显示，渲染前会被清掉，不会印进正文。
- 扉页只有书名、作者与封面图，不写来源；默认没有书前目录（`--toc` 才排）。命令输出的
  「扉页」一行说明封面进没进去；缺封面会进验收警告，扉页不留空段。
- **图片格式**：python-docx 只认 PNG、带 JFIF/Exif 头的 JPEG、GIF、TIFF、BMP。微信读书
  封面图床的 JPEG 多半**没有 JFIF 头**（开头直接是 `FF D8 FF DB`），异常原先被 `except`
  吞掉，26 本里 21 本扉页没封面、验收照样通过（2026-09-14 修）。现在图片统一走
  `ImageStore.for_docx`：先无损补 JFIF 头，不行再用 Pillow 重编码（webp、Exif 段坏掉的
  JPEG），缓存里的原图不动。仍嵌不进去的，块图留「〔图片无法嵌入〕」、随文图留高亮〔?〕，
  验收都会报，空的图段落也会报。
- 标题用自建的 `WR 标题一～四` 样式（黑色，带大纲级别），不用 Word 内置的蓝色
  `Heading`/`Title`。其余自建样式：`WR 图`、`WR 图说`、`WR 引文`、`WR 落款`、
  `WR 表格文字`、`WR 尾注`、`WR 分隔`。
- **任务目录**在 `<WEREAD_WORK_DIR>/<bookId>-<书名>/`（默认技能目录下 `work/`），是**可丢的缓存**：
  `book.json`（书目+章节表）、`xhtml/`（原始正文）、`css/`、`images/`、
  `progress.json`（续跑用）、`docx-audit.json`（验收报告）、
  `docx-rejected.docx`（验收没过的候选件，成品不会被它覆盖）。留着的唯一好处是改样式时能 `weread build` 重生成而
  不必重抓；删掉只是下次要重抓，不丢任何判断——人工判读记在 `.state/pua_manual.json`，
  不在这里。一本书大约 1–12MB。

## selftest 覆盖面

`weread selftest` 的夹具覆盖表格合并、各种注释写法（含跨文件）、随文图、样式映射、
拆行的章标题、多文件章的黑体、封面与认不出的图片格式、书前目录、册数题名，以及验收能否抓出这些老毛病。

## 排版核查的两个坑（2026-09-19《毛泽东文集》）

- LibreOffice 用中华书局宋体渲染时，书名号内的字会丢成空《》。docx XML、`textutil`、Word 渲染都正常；改动前交付的《神文时代》同样出现 2380 处，确属渲染器问题。
- 当时为求证改用 AppleScript 驱动 Word 导出 PDF：先弹沙盒授权窗（完全磁盘访问管不了沙盒），大文档导出又报「连接到网络时出现问题」并超时，最后只能强杀 Word。故禁用 Word/WPS 做核查。
